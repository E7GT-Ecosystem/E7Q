# Exact qubit quantum-view adapter fixture

This is an opt-in E7Q research adapter, `e7q.quantum-view/0alpha1`, separate from Q-A1/Q-A2 and #79's EEC-Q formal-rational planner. The implementation uses exact rational real/imaginary parts for 2×2 qubit matrices.

## Reproduce

From the E7Q repository root:

```bash
python -m pytest tests/test_quantum_view_v0alpha1.py -q
python scripts/quantum_view_numpy_check.py
```

The fixture declares `rho±=(I±(1/2)Y)/2` and records exact X/Y/Z Born probabilities and the two distinct reconstruction fibres. Two density operators lie in the selected X/Z state fibre; three preparation descriptions lie in its preparation-description fibre because two descriptions alias `rho+`.

For joint devices, sharp X/Z returns a checked support-intersection obstruction certificate. The unsharp `eta=1/2` case returns a constructed parent only after exact checks of positivity, normalization, and each marginal. Other valid `eta` values without a checked witness or obstruction return `undetermined`.

Fibre queries validate every observed context, canonical outcome label, exact rational probability, probability range, and normalization before searching; malformed observations return `invalid_input`, and unknown Pauli contexts return `unsupported`. A supplied normalized positive candidate with the wrong marginals returns `undetermined`, except at `eta=1`, where the independently verified sharp X/Z obstruction still yields `incompatible`.

`ResourcePolicy.max_operations` is an accounting budget: each requested state/context Born distribution costs 12 fixed work units. Aggregate views and fibres preflight the complete charge, so a view of 129 contexts exceeds the default budget of 128. This budget bounds the count of adapter-accounted Born evaluations, not numerator/denominator bit growth or wall-clock time of Python's exact `Fraction` arithmetic.

`independent_numpy_result.json` is generated by a separate direct-matrix NumPy script that imports no adapter code. It is a finite numerical cross-check of the exact fixture, not a proof. It does not validate physical records or establish a product or physics claim. Physical outcomes are imported as provenance-bearing records; seeded simulator outputs have a different type and are always labelled simulated.
